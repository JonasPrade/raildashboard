## Roadmap-Steuerung

Die Roadmap wird über ein **GitHub-Projects-Board** gesteuert — Regeln für die
Zusammenarbeit (Status-Wechsel, Issue-Format, User-Backlog, Release-Gate) stehen
in [`docs/github-projects.md`](docs/github-projects.md). `docs/roadmap.md` ist
nur noch Lese-Übersicht; lose Ideen kommen in `docs/user-backlog.md`.

**Auto-Merge ist eingeschaltet.** Ein `PostToolUse`-Hook (`.claude/settings.json` →
`.claude/hooks/pr_auto_merge.py`) meldet sich, sobald ein PR angelegt ist, und gibt den
dauerhaften Auftrag mit: CI verfolgen, rote Läufe beheben, bis sie grün ist, dann ohne
Rückfrage mergen (Merge-Commit). Ausnahme: Issue in **Needs User Test** oder Draft-PR —
dann bei Grün anhalten. Ein Merge auf `master` rollt nicht aus. Hook-Eintrag entfernen
schaltet es ab.

## Alembic / Database Migrations

Use the Makefile commands for all Alembic interactions — never call `alembic` directly.

| Task | Command |
|---|---|
| Apply all pending migrations | `make migrate` |
| Create a new autogenerated revision | `make migrate-create MSG="describe the change"` |
| Run migrations inside Docker container | `make docker-migrate` |

## Deployment (Dispatch per Commit-SHA)

Produktion läuft auf dem Contabo-Host `vmd92747` und wird **von Hand per Knopf** ausgerollt,
nicht mehr per Tag. Vertrag: [`DEPLOY.md`](DEPLOY.md), Begründungen und Ausnahmen:
[`docs/workflow.md`](docs/workflow.md), Handschritte: [`docs/uebergabe-deploy.md`](docs/uebergabe-deploy.md).
Vor jeder Änderung am Deploy-Ablauf beide zuerst lesen.

- `ci.yml` (`pull_request`, Job **`Prüfung`**) und `release.yml` (`push [master]`) fahren
  **`make test`** und sonst nichts; `release.yml` schiebt danach
  `ghcr.io/jonasprade/raildashboard-{backend,frontend,db,graphhopper}:<commit-sha>` nach GHCR.
- `deploy.yml` (`workflow_dispatch`): SHA leer = `master`, Rollback = frühere SHA. Prod zieht,
  baut nie. Einen Deploy startet nur ein Mensch.
- Tags (`CHANGELOG.md`) benennen Stände, rollen aber nichts aus.

Konsequenzen für Änderungen:
- **Ein Kommando prüft alles: `make test`.** Es läuft in den `test`/`check`-Stufen der
  Dockerfiles; die CI hat keine eigenen Schritte. Für die schnelle Schleife: `make test-local`.
- `compose.yaml` referenziert nur GHCR-Images (`image:`), **nie** `build:` — lokale Builds
  gehören in `compose.override.yaml`. Kein `0.0.0.0`-Port: der Host-nginx erreicht das
  Frontend über `127.0.0.1:5000`.
- **`/healthz` ist das Deploy-Tor**: neue harte Abhängigkeiten dort mit abdecken.
- Migrationen rückwärtskompatibel (Expand/Contract); das Backup vor der Migration macht der
  One-shot-Dienst `backup`, der Entrypoint überspringt die Migration bei einer DB, die weiter
  ist als der Code (`apps/backend/scripts/db_ahead.py`).
- `apps/backend/requirements.txt` bleibt exakt (`==`) gepinnt.
- Neue **Pflicht-Felder in `Settings`** (`core/config.py`) brauchen einen Default in
  `apps/backend/tests/conftest.py` (`os.environ.setdefault(...)`), sonst bricht `make test`
  auf einem sauberen Checkout ohne `.env`.
- Bei Deploy-relevanten Änderungen `CHANGELOG.md`, `DEPLOY.md` **und**
  `docs/production_setup.md` nachziehen.
